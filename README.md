# ACT Smart City Dashboard

แดชบอร์ดเมืองอัจฉริยะสำหรับ Assumption College Thonburi ใช้ Next.js App Router, React และ TypeScript พร้อมตัวเชื่อมต่อ PostgreSQL/Supabase, SQLite และ Cloudflare D1

## หน้าภาพรวม

- ใช้พื้นขาวและเมนูกรมท่า แสดงข้อมูลทั้งเมืองในหน้าเดียว
- สรุปจำนวนอุปกรณ์ที่เคยรายงานข้อมูล อุปกรณ์ออนไลน์ แจ้งเตือน และออฟไลน์
- แสดงสภาพอากาศจากสถานีที่เลือก: PM2.5 อุณหภูมิ และความชื้น
- แผงสถานะ 5 ระบบ: ที่จอดรถ สัญญาณจราจร ไฟถนน ประตู RFID และสิ่งแวดล้อม
- กราฟค่าฝุ่นย้อนหลัง ตำแหน่งอุปกรณ์จากพิกัดจริง และรายการข้อมูลรับเข้าล่าสุด
- รีเฟรชข้อมูลทุก 5 วินาที ส่งออก CSV และขยายมุมมองโดยซ่อนเมนูได้
- รองรับจอเดสก์ท็อปและมือถือ; เปิดรายละเอียดระบบโดยคลิกแผงของระบบนั้น
- ตัวควบคุมหลักใช้ HeroUI v3 ทั้งการ์ดสรุป ปุ่ม ช่องกรอก ตัวเลือกสถานี/คำสั่ง/ข้อมูลบัตร และ AlertDialog ที่ยืนยันก่อนส่งคำสั่งอุปกรณ์หรือลบบัตร RFID
- ผังที่จอดรถใช้ชื่อช่องจากข้อมูลจริงหรือชื่ออุปกรณ์ ไม่สร้างทะเบียนรถหรือรหัสช่องขึ้นเอง; แผงไฟถนนไม่แสดงค่าพลังงานประหยัดที่คำนวณจากสมมติฐาน
- รูปแบบ Apple-inspired ใช้พื้นที่ว่าง ตัวอักษรชัดเจน การ์ดพื้นขาวมุมโค้ง สีอ่อนและเงาบาง ปรับตามขนาดจอ โดยยังแสดงข้อมูลว่างตามจริงและคงเมนูกรมท่า

## นโยบายข้อมูลจริงเท่านั้น

ไม่มีโหมดสาธิต API จำลองเหตุการณ์ การสุ่มค่า หรือการสร้างข้อมูลอุปกรณ์ตั้งต้น ข้อมูลที่อ่านผ่านชั้น storage ต้องเป็น `source: live`

เมื่อยังไม่มีข้อมูล หน้าจอแสดงสถานะรอข้อมูลและเครื่องหมาย `—` โดยไม่สร้างตัวเลข กราฟ หรือตำแหน่งทดแทน เมื่อฐานข้อมูลอ่านไม่ได้ API Dashboard ตอบ HTTP 503 และหน้าจอแจ้งข้อผิดพลาด หากเคยโหลดข้อมูลสำเร็จ จะแสดงชัดเจนว่าเป็นข้อมูลครั้งก่อน

ค่าปัจจุบันบนหน้าภาพรวมใช้เฉพาะอุปกรณ์ที่ยังไม่ออฟไลน์ ส่วนกราฟและบันทึกเป็นประวัติที่ได้รับล่าสุด ไม่ใช่การรับประกันช่วงข้อมูล 24 ชั่วโมง จำนวนอุปกรณ์หมายถึงอุปกรณ์ที่มี telemetry ในฐานข้อมูล ไม่ใช่ทะเบียนอุปกรณ์ที่ยังไม่เคยส่งข้อมูล

`src/lib/data-integrity.ts` กรองรายการตัวอย่างจากตัวติดตั้งรุ่นเก่าที่ถูกบันทึกเป็น Live โดยตรวจลักษณะข้อมูลที่รู้จัก และกรองบัตร RFID ตัวอย่างเดิมที่ยังไม่ได้แก้ไข ข้อมูลเหล่านั้นไม่ได้ถูกลบจากฐานข้อมูล ตัวกรองนี้ไม่ใช่ระบบยืนยันแหล่งกำเนิดข้อมูลทั่วไป หากเปลี่ยนข้อมูลตัวอย่างนอกแอป ต้องตรวจสอบแหล่งที่มาเพิ่มเติม

## เริ่มใช้งาน

```bash
npm install
npm run dev
```

เปิด [Dashboard ในเครื่อง](http://localhost:3000) และตั้งค่า `.env.local` ด้วยค่าของสภาพแวดล้อมที่ใช้งานจริง ห้าม commit ไฟล์นี้หรือใส่ token จริงในเอกสาร

| ตัวแปร | การใช้งาน |
| --- | --- |
| `DB_DRIVER` | `postgres` (ค่าเริ่มต้น), `sqlite` หรือ `d1` |
| `SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_URL` | URL ของ Supabase |
| `SUPABASE_ANON_KEY` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Key สำหรับ Supabase ตามสิทธิ์ที่ตั้งไว้ |
| `SUPABASE_SERVICE_ROLE_KEY` | Key เฉพาะเซิร์ฟเวอร์สำหรับ API ทะเบียนบัตร ห้ามใส่ `NEXT_PUBLIC_` หรือส่งเข้า browser |
| `RFID_ADMIN_TOKEN` | Bearer token สำหรับเปิดทะเบียนและเพิ่ม แก้ไข ลบบัตร |
| `INGEST_TOKEN` | Bearer token สำหรับรับ telemetry ผ่าน API |
| `SETTINGS_TOKEN` | สิทธิ์อ่าน audit และแก้การตั้งค่าโหมด |
| `CONTROL_TOKEN`, `OPERATOR_NAME` | Token และชื่อผู้สั่งควบคุมอุปกรณ์ |
| `CONTROL_OPERATORS_JSON` | ทางเลือกสำหรับกำหนดผู้สั่งและ token หลายคน |
| `DEVICE_COMMAND_URL`, `DEVICE_COMMAND_TOKEN` | ตัวเชื่อมต่อส่งคำสั่งไปยังฮาร์ดแวร์ |
| `OFFLINE_AFTER_SECONDS` | เกณฑ์ออฟไลน์ฝั่งเซิร์ฟเวอร์ ค่าเริ่มต้น 120 วินาที |
| `DB_PATH` | ที่เก็บ SQLite เมื่อเลือก driver นี้ |
| `CF_ACCOUNT_ID`, `CF_D1_DATABASE_ID`, `CF_API_TOKEN` | การเชื่อมต่อ D1 |

ทะเบียน RFID ใช้ `SUPABASE_SERVICE_ROLE_KEY` บนเซิร์ฟเวอร์และ `RFID_ADMIN_TOKEN` ที่ผู้ดูแลกรอกในหน้าประตู ส่วนเฟิร์มแวร์บอร์ด 1 ยังอ่านทะเบียนบัตรและบันทึกการสแกนด้วย publishable key จึงต้องคงสิทธิ์อ่านบัตรและเพิ่ม log ตาม migration ด้านล่าง Wi-Fi ยังใช้การเชื่อมต่อเดิม

สร้างตารางใน Supabase ด้วย `supabase_schema.sql` ซึ่งไม่มีการเติม telemetry หรือบัตรตัวอย่างแล้ว ตารางหลักคือ `events`, `settings`, `rfid_cards`, `gate_logs` และ `command_audit`

ฐานข้อมูลที่ติดตั้งรุ่นก่อนต้องรัน `supabase/migrations/20260927_rfid_access.sql` ใน Supabase SQL Editor ก่อนเปิดใช้งานทะเบียนบัตรรุ่นนี้ สคริปต์ปรับ RLS/grants โดยไม่ลบข้อมูล: publishable key อ่านบัตรและเพิ่มประวัติการสแกนได้ตามที่บอร์ด 1 ใช้ แต่เพิ่ม/แก้ไข/ลบบัตรไม่ได้ ตั้งค่า secret ทั้งสองในสภาพแวดล้อมของเซิร์ฟเวอร์และรีสตาร์ตแอป หากขาดค่าระบบจะแจ้งว่าไม่พร้อมใช้งาน แนะนำตั้ง token แบบสุ่มยาวและจำกัดการเข้าถึงหน้าแอปเพิ่มเติม

ในหน้า “ประตู RFID” เปิดทะเบียนด้วย `RFID_ADMIN_TOKEN` แล้วเพิ่มบัตรด้วย UID จากเครื่องอ่านจริง (เลขฐานสิบหก 8, 14 หรือ 20 ตัว) ชื่อ ประเภท และสถานะ บัตรใหม่เริ่มที่ “ระงับ” ต้องเลือก “อนุญาต” อย่างชัดเจนก่อนใช้ผ่านประตู การแก้ไขไม่เปลี่ยน UID การลบต้องยืนยัน หน้าจอจะแสดงผลจากฐานข้อมูลจริงและไม่สร้างบัตรตัวอย่าง

## API

| Endpoint | หน้าที่ |
| --- | --- |
| `GET /api/dashboard` | ข้อมูลอุปกรณ์ล่าสุด สถานะ ประวัติ และเวลาเซิร์ฟเวอร์ |
| `POST /api/ingest` | รับ telemetry ที่ตรวจ schema แล้ว; ต้องใช้ `INGEST_TOKEN` |
| `GET /api/rfid` | อ่านบัตร 500 รายการล่าสุดและประวัติ 50 รายการ; ต้องใช้ `RFID_ADMIN_TOKEN` |
| `POST /api/rfid` | เพิ่ม UID ใหม่เท่านั้น; บัตรซ้ำตอบ 409; ต้องใช้ `RFID_ADMIN_TOKEN` |
| `PATCH /api/rfid?card_id=...` | แก้ชื่อ ประเภท และสถานะ โดย UID คงเดิม; ต้องใช้ `RFID_ADMIN_TOKEN` |
| `DELETE /api/rfid?card_id=...` | ลบบัตร RFID; ต้องใช้ `RFID_ADMIN_TOKEN` |
| `GET /api/settings` | รายงานการตั้งค่าการเชื่อมต่อ |
| `PATCH /api/settings` | รองรับเฉพาะ `{ "mode": "live" }`; ต้องใช้ `SETTINGS_TOKEN` |
| `GET /api/settings/wifi` | อ่านค่า Wi-Fi ที่บันทึกไว้ |
| `POST /api/settings/wifi` | บันทึกค่า Wi-Fi; จะไม่รายงานสำเร็จหากฐานข้อมูลปฏิเสธ |
| `POST /api/control` | ส่งคำสั่งผ่าน adapter สำหรับอุปกรณ์ออนไลน์ทั้ง 5 บอร์ด; ต้องยืนยันผู้สั่ง |
| `GET /api/audit` | อ่านประวัติคำสั่งด้วย `SETTINGS_TOKEN` |

API จำลองเหตุการณ์และหน้าทดสอบ SSR เดิมถูกนำออกแล้ว

## ฮาร์ดแวร์

ซอร์สของบอร์ดอยู่ใน `Arduino/Board_1` ถึง `Arduino/Board_6` ตามลำดับ: RFID Gate In (GT-1), Traffic Light (TR-1), Parking (PK-1), Environment (EN-1), Street Light (SL-1) และ RFID Gate Out (GT-2) อ่านรายละเอียดการต่อวงจรและติดตั้งจาก `Arduino/README.md` และ `Arduino/WIRE.md`

เฟิร์มแวร์รุ่นนี้เอาวันเวลาและพิกัดที่เขียนค้างไว้ในโค้ดออกแล้ว และย้ายค่าการเชื่อมต่อที่ต้องกำหนดจริงไปยัง `SmartCitySecrets.h` เฉพาะเครื่อง (คัดลอกจากไฟล์ `.example.h` ของแต่ละบอร์ด) บอร์ดจอดรถ (PK-1) รายงานจำนวนช่องว่างและความจุรวม 8 ช่อง พร้อมแสดงเวลา NTP กองทัพเรือบน OLED บอร์ดสิ่งแวดล้อมไม่แปลง MQ-2 เป็น PM2.5; หน้า Dashboard จะแสดง `—` สำหรับ PM2.5 จนมีเซ็นเซอร์ฝุ่นจริง บอร์ด 2 และ 5 มีระบบ auto-reconnect และจัดการ SSL sockets เพื่อป้องกันสถานะ offline

สำหรับ **Board 5 (ไฟถนน)** และ **Board 6 (ประตู RFID ขาออก)** แนะนำให้ใช้ **ESP32** (ไม่แนะนำ ESP8266 เนื่องจากขา GPIO ไม่เพียงพอต่อการต่อโมดูลพร้อมกัน และ RAM จำกัดเมื่อคุย TLS/HTTPS ไปยัง Supabase):
- **Board 5 (ESP32):** LDR อ่านค่าแสงใช้ Pin `GPIO 34` (ADC1), PIR ตรวจจับคน/รถใช้ `GPIO 27`, PWM ขับไฟถนนใช้ `GPIO 18`
- **Board 6 (ESP32):** RC522 (SPI) ใช้ `SS: 5, RST: 4, SCK: 18, MISO: 19, MOSI: 21`, จอ LCD I2C ใช้ `SDA: 23, SCL: 22`, Buzzer ใช้ `GPIO 25`, ประตูเปิดใช้ `GPIO 14` รายละเอียดการต่อสายทั้งหมดอ่านได้ใน `Arduino/WIRE.md`

หน้าจอที่แสดงค่าว่างยังไม่ยืนยันว่าฮาร์ดแวร์เสีย ต้องตรวจการเชื่อมต่อและดูว่ามีข้อมูลที่มาจากอุปกรณ์จริงส่งเข้ามาหรือไม่

ซอร์สบอร์ด 1 เปลี่ยนกรณี Wi-Fi หลุดให้ปฏิเสธการเปิดประตู แต่ต้องแฟลชเฟิร์มแวร์ใหม่บนอุปกรณ์จริงจึงมีผล และยังไม่ได้ทดสอบกับฮาร์ดแวร์

## ข้อจำกัดที่ต้องทราบ

- PostgreSQL latest query อ่านล่าสุด 60 แถวก่อนแยกตาม device; fleet ขนาดใหญ่หรืออุปกรณ์ที่ส่งถี่อาจต้องใช้ latest-per-device query ฝั่งฐานข้อมูล
- หน้า client ใช้เกณฑ์ออฟไลน์เริ่มต้น 120 วินาที; การตั้ง `OFFLINE_AFTER_SECONDS` เป็นค่าอื่นฝั่งเซิร์ฟเวอร์ยังไม่ได้ส่งต่อไปยัง client
- ต้องนำ migration ไปใช้กับฐานข้อมูลจริงและตั้งค่า secret ก่อนจึงใช้งานทะเบียนบัตรได้; การ build ไม่ได้ยืนยันขั้นตอนนี้
- เฟิร์มแวร์ปัจจุบันยังต้องอ่านข้อมูลผู้ถือบัตรด้วย publishable key และส่ง log โดยตรง จึงยังมีความเสี่ยงด้านการเปิดเผยข้อมูลและ log ปลอม รวมถึงค่า credential/TLS ในเฟิร์มแวร์ที่ต้องออกแบบใหม่ก่อนเปิดสาธารณะ
- ค่า token/Wi-Fi ที่เคยอยู่ในประวัติ Git ต้องเปลี่ยนก่อนนำระบบไปใช้งานจริง; source ใหม่ไม่ได้ส่งรหัส Wi-Fi ไปตาราง `settings` แล้ว แต่ไม่ได้ลบข้อมูลเดิมในฐานข้อมูล
- บอร์ด 3 ยังไม่มีเซ็นเซอร์ตรวจแต่ละช่องหรือจุดอ้างอิง occupancy หลังรีบูต จึงไม่มีข้อมูลช่องว่างจริงสำหรับแผงจอดรถ; บอร์ด 4 ยังไม่มี PM2.5 sensor
- หน้าทะเบียนโหลดบัตรล่าสุดสูงสุด 500 ใบ; การค้นหาในหน้าใช้เฉพาะรายการที่โหลด ไม่ใช่การค้นหาทั้งฐานข้อมูล
- การตั้งค่า Wi-Fi ยังต้องตรวจสอบสิทธิ์แยกต่างหากก่อนใช้งานสาธารณะ
- ทดสอบหน้าจอและ build ในเครื่องแล้ว ยังไม่ได้ยืนยันกับฮาร์ดแวร์จริงหรือ deployment ภายนอก

ปุ่มหุบ/เปิดเมนูอยู่มุมซ้ายของแถบด้านบนทุกหน้า บนเดสก์ท็อปจะซ่อนเมนูทั้งแถบและจำสถานะไว้ในเบราว์เซอร์ บนมือถือจะเปิดเป็นแผงทับหน้าจอ ปิดได้ด้วยปุ่มปิด แตะพื้นหลัง หรือกด Escape
